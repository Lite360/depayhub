10. Provider Architecture

Do not hard-code the application directly against one VTU provider.

Create a provider adapter layer.

ProviderManager
       │
       ├── VTU Naija
       ├── Inlomax
       ├── LixzDataSub
       ├── PaymentPoint
       ├── Aspify
       └── NIN Provider

Each provider should implement standardized methods.

Example:

purchaseAirtime()
purchaseData()
purchaseCable()
purchaseElectricity()
checkTransaction()
getBalance()

This allows admin to change providers without rebuilding the entire platform.

11. Provider Failover

For services where multiple providers are available:

Primary Provider
      ↓
Failure
      ↓
Secondary Provider

But failover must be carefully controlled.

Never automatically retry a financial transaction if the first provider may have already processed it.

Use provider transaction status/reconciliation first.

29. Master Development Prompt

Use this as the main prompt when giving the project to an AI coding agent:

Build a production-ready Nigerian VTU and digital payment platform called DEPAYHUB.


Design the project to deploy on Vercel.


Use environment variables for all secrets.


Never put provider API secrets in React/Vite client-side variables.


Use Neon PostgreSQL for production database.


Use Vercel Blob for file storage.


DATABASE:


Create proper Prisma schema and migrations.


Use UUID/CUID identifiers as appropriate.


Use unique constraints for:
- usernames
- emails
- references
- webhook event IDs
- API key identifiers


Use database transactions for wallet operations.


Do not use floating point for money.
Store monetary values using PostgreSQL NUMERIC/DECIMAL or integer minor units.


DOCUMENTATION:


Generate:
- README
- Environment variable documentation
- API documentation
- Database schema documentation
- Deployment guide
- Security guide
- Provider integration guide


Build the system modularly and avoid duplicated business logic.


Never place financial logic in React.


Never trust client-supplied:
- price
- role
- wallet balance
- transaction status
- provider status


The backend is the source of truth.


Start by generating the architecture, database schema, route structure and authentication model before implementing individual services.
MVP launch target

For the first real Depayhub release, I would keep the launch scope to:

Registration → Subscriber dashboard → Wallet → PaymentPoint/Aspify funding → Airtime/Data → Cable/Electricity → Transactions → Receipts → Email alerts → Admin pricing → Vendor application.

Then add NIN/BVN, public API, advanced fraud detection, referrals and sophisticated marketing after the core wallet/payment flow has been properly tested.

That gives you a much safer MVP than trying to launch every module at once.
